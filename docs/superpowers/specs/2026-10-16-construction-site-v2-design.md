# Construction site V2 design

**Date:** 2026-10-16
**Branch:** `site-overhaul` (from `main` at `fcf6b65`)
**Input:** docs/superpowers/specs/2026-10-13-construction-site-overhaul-brief.md (the brief)
**Before:** Phase 4B runs on this site.

## 1. Purpose and scope

`ConstructionSiteV1` grew one test at a time and does not read as a construction site. This
design builds a new scene, `ConstructionSiteV2`, that looks like an organized site (zones,
marked lanes, nothing floating or intersecting) and contains every test feature of brief
Section 3 where a real site would have it. V1, its exports and `config/scenarios.yaml` stay
unchanged: the frozen baselines (tag `baselines-2026-10-13`) ran on them.

The design also makes the site an explicit input of the whole stack: every scenario names its
site, and the runner, the demo, Nav2, MoveIt and the MPC load that site's map and boxes and
the matching Unity scene.

It adds one thing the brief excluded: switchable terrain disturbances on the lanes (Section 5).

### Decisions taken in the design discussion

| Topic | Decision |
|---|---|
| Authoring | Hybrid kit. An editor command builds everything that matters for navigation or collision from a grid-aligned modular kit; each kit piece carries its own box proxies. Pure decoration lives in a root the builder never touches and can be tuned by hand in the Editor. |
| Asset source | By role. Walls, columns, beams and slabs are Unity primitives with a shared tiled material set. Scaffold, fences, cabins, pallets and stacks, barriers, pipe rack and the Tier 2 pieces are low-poly meshes from headless Blender scripts. Existing Megascans scans only as optional small dressing. |
| Source of truth | One kit spec JSON holds every piece's dimensions and proxies; the Blender scripts and the Unity builder both read it. The layout is typed C# in the V2 builder. |
| Map selection | One scenario file per site. `scenarios_site_v2.yaml` declares `site: construction_site_v2`; `scenarios.yaml` implicitly means `construction_site`. A single `site` launch argument and parameter replaces every hard-coded map path. |
| Unity scene | Switched automatically by the runner and the demo through a new CLI command; the scene path is recorded in each run. |
| Layout | Option A, "spine road", 50 x 40 m (Section 4). Option B (ring road) was rejected: Nav2 could route round the overhead test, and ring traffic passes features unrelated scenarios do not need. |
| Terrain | Tier 1: decorative terrain off the lanes. Tier 2: disturbances on the lanes below the lidar's 0.05 m band, switchable per scenario. Tier 3 (slopes and ramps) out of scope. This amends brief requirement 6 (flat drivable floor) for Tier 2 only. |
| Modelling tool | Blender 5.2.2 LTS on the development Mac, run headless (`Blender --background --factory-startup --python ...`), no Blender MCP. FBX export and Workbench preview renders verified on 2026-10-16. |

### Facts this design relies on

- The lidar (`IidNoiseRaycastLiDARSensor`) is a physics raycast: it sees colliders, not meshes.
- `GroundTruthBaseTfPublisher` publishes the full 3D base rotation and height, so a tilted
  base still places lidar points correctly in the map frame. Only geometry at least 0.05 m
  above the floor is marked as an obstacle (`base_band` and the B1-B4 bands start at 0.05 m).
- The floor friction (0.05 static / 0.02 dynamic, friction combine minimum) was tuned for
  skid-steer in-place turns (docs/unity-skid-steer-base-controller.md).
- `motion-planning-sim/Assets/Models/` is git-ignored: V1's Megascans dressing is not in the
  repository.
- V1 is generated by `build_construction_site` in `ConstructionSiteTools.cs`; the Phase 4
  overhead beam and course gate posts are scenario obstacles, not scene geometry.
- The path `maps/construction_site.*` is hard-coded in `global_planning.launch.py`,
  `scenario_spec.cpp`, `planning_scene_loader.cpp`, `wholebody_mpc_node.cpp` and
  `clearance_3d.cpp`; `scenarios.yaml` is loaded directly in `planning_scene_loader.cpp`,
  `octomap_box_check.cpp`, `scenario_spec_main.cpp` and `tools/demo.py`.

### Out of scope

- MPC, Nav2, MoveIt or controller changes (Phase 4B and later).
- Baseline reruns. One final baseline run on the final site happens before the thesis tables
  (roadmap comparability log).
- Perceived-obstacle mapping.
- Animated worker figures (movers stay boxes), a switchable cross-fall, slopes and ramps
  (Section 11).

## 2. Architecture

### Kit

- `tools/site_kit/kit_v2.json`: for every piece, its mesh dimensions, its box proxies (local
  centre, size, yaw), its material and its physics material. It also holds the overhead
  member heights H1-H3 (Section 4) once computed.
- `tools/blender/site_kit/`: one headless script per piece family plus `build_kit.py`, which
  reads the spec, exports FBX to `motion-planning-sim/Assets/SiteKit/Meshes/` and renders a
  preview PNG of each piece. The scripts check `bpy.app.version` against the pinned 5.2 LTS.
- `motion-planning-sim/Assets/SiteKit/` (`Meshes/`, `Materials/`, `Textures/`) is committed,
  so a host without Blender still gets the full site. It must not sit under a folder named
  `Models/` (git-ignored).

### Unity editor code

- `SiteKit.cs` places one piece: the visual instance under its zone in
  `Environment/Structural`, its proxies as `BoxCollider`s under
  `Environment/NavigationObstacles/<Zone>/<Piece>`. Visual meshes get no colliders, so
  physics, the lidar, the exported boxes and every planner see the same geometry. At build
  time it compares each imported mesh's bounds with the spec (tolerance 0.02 m). A piece
  whose FBX is missing is placed as a primitive placeholder sized from the spec, so Unity
  work never waits on Blender.
- `ConstructionSiteV2Builder.cs` adds `build_construction_site_v2` (one method per zone). It
  opens `Assets/Scenes/ConstructionSiteV2.unity`, rebuilds only its generated roots
  (`Environment/Ground`, `Environment/Structural`, `Environment/NavigationObstacles`,
  `Environment/Disturbances`, `Experiment`, lighting and cameras) and never touches
  `Environment/HandDressing`. Megascans dressing is placed only when the scan exists locally.
- `validate_construction_site_v2` checks:
  - proxies lie inside the map;
  - no two proxies intersect unless the pair is declared as a joint;
  - every proxy whose bottom is above 0.01 m rests on the ground or on another proxy
    (within 0.01 m);
  - the feature dimensions of Section 4: door clear widths, straight approaches, lane widths,
    the open area, and H1-H3 against the pose heights.
- `Nav2MapExporter` and `PlanningBoxExporter` take a site (scene path and output name, map
  size) and write `maps/<site>.pgm|yaml|boxes.yaml|metadata.json`. V1's outputs stay
  byte-identical (tested). `Environment/Disturbances` is never exported.
- New CLI commands:
  - `site_open <scene>` (Edit mode): opens the scene, a no-op when it is already active;
  - `site_disturbances on|off` (Play only, like the scenario commands): activates or
    deactivates `Environment/Disturbances`.

### ROS

- The existing C++ `ScenarioConfig` becomes the single resolver. It reads every
  `config/scenarios*.yaml`; a file's optional top-level `site:` defaults to
  `construction_site`. `resolve(name)` returns the scenario and its site; a name defined in
  two files is an error. `map()` and the boxes path take the site. The direct
  `load("scenarios.yaml")` calls switch to `resolve()`.
- Nodes that load the world (`planning_scene_loader`, `wholebody_mpc_node`, `clearance_3d`,
  `octomap_box_check`) get a `site` parameter; the `boxes_file` default becomes
  `maps/<site>.boxes.yaml`. When a scenario is given, its site wins, and an explicit `site`
  that disagrees is an error.
- Launch argument `site` (default `construction_site`) in the navigation, global planning,
  manipulation and MPC launches. V1 commands run unchanged.
- `maps/<site>.metadata.json` already carries `sourceScene` and the map size (`widthCells`, `heightCells`, origin, resolution); the existing `sourceScene` key is used, nothing is added.
- `scenario_spec` output gains `site`, `scene` and `disturbances`.

### Runner and demo

- `tools/run_nav_scenario.py` reads `site`, `scene` and `disturbances` from `scenario_spec`.
  Before the Play epoch it stops Play if the scene must change, calls `site_open <scene>`,
  enters Play, and calls `site_disturbances on` when the scenario asks for it. Disturbances
  are switched off at the end of the run and at every new epoch. It passes `site:=` to every
  launch and records site, scene and disturbances in the run JSON.
- `tools/demo.py` takes `--site` (or the site of a given scenario), opens the scene and serves
  that site's map.

## 3. Kit pieces and assets

### Pieces

| Source | Pieces |
|---|---|
| Unity primitives | Blockwork wall (0.2 m thick, parametric length, 3.0 m high), reinforced-concrete column, beams, stair and lift core, slab finish flush with the floor (visual only) |
| Blender | Scaffold standards with base plates, ledgers, transoms, boards and toe boards on 2.5 x 1.2 m bays; mesh fence panels on concrete feet; plywood hoarding; 20 ft site cabins (office, welfare, drying room); Euro pallets with block, bag and panel stacks; timber and rebar on bearers; precast block barriers 0.8 m; pipe rack with T-supports and the pipe bridge; skip; IBC tank; cable protector, road plate, rumble strip (Tier 2) |

The overhead members H1 is a real scaffold ledger, and H3 is the pipe
bridge, each carried by standards or supports.

### Proxy rule

Proxies enclose the mesh and are never smaller than it. Square sections get under 0.02 m of
error. Round pipes and tubes get one box per pipe (the corner overshoot is conservative).
Barriers are boxy precast blocks rather than tapered Jersey barriers so one box fits.

### Materials

One shared HDRP Lit set from CC0 tileable textures at 1K (ambientCG or Poly Haven),
committed under `Assets/SiteKit/Textures/`: asphalt (spine), compacted ground, gravel,
concrete, blockwork, timber, galvanized steel, painted steel, plastic, cabin paint, plus lane
marking and walkway decals. No other materials on V2 kit pieces, so colours stay consistent.

### Performance

Static pieces are marked static for batching; shared materials use GPU instancing; no LODs.
V1's lighting rig (realtime sun, exposure volume, fill lights) is reused. The real-time
factor is measured with the same run on V1 and V2 (Section 7); baked lighting is the fallback
if V2 drops below 1.00.

## 4. Layout

### Frame and grid

ROS map frame, centred on the site: x -25 to 25 m, y -20 to 20 m, origin [-25, -20, 0],
resolution 0.05 m (1000 x 800 cells). The Unity-ROS axis mapping is V1's. The plan audits
every place that assumes 40 x 40 m (costmap bounds, exporter sizes, validators, tests) and
parameterizes it by site. Placement uses a 0.1 m grid, a 0.5 m module for walls, and yaw in
multiples of 90 degrees unless a piece declares otherwise.

### Overhead heights

Bottom-of-member heights, computed by FK from the qualified poses
(`qualified_payload.json`: `home`, `vertical_carry`, `carry`) before the build and written to
the kit spec:

| Member | Rule |
|---|---|
| H1 scaffold ledger | Carry panel top + 0.10 m, and at least 0.10 m below the home panel top (about 1.565 m) and the vertical-carry panel top (about 1.92 m). Only `carry` passes. |
| H3 pipe bridge | 2.40 m. Every pose passes (control). |

H2 (a member that needs reorientation) is dropped for this phase: FK puts the carry top at 1.320 m and no qualified held pose is lower (lowest `lowered`, 1.458 m), so no qualified configuration could pass it (decided 2026-10-16).

If the carry panel top makes H1 incompatible with the home or vertical-carry limit, the plan
stops and the heights go back to the user.

## 5. Terrain

### Tier 1 (decorative, always present)

Off the lanes. Anything the base could reach gets a proxy: spoil heaps get stepped box
proxies (mapped as obstacles); an open trench is below the lidar band and invisible to it, so
it sits inside proxied barriers. Lane and walkway markings are flush decals.

### Tier 2 (disturbances, switchable)

On the lanes, under `Environment/Disturbances`, inactive by default, not exported to the map
or the planning boxes (planners do not know about them, by design). Heights at most 0.035 m
with chamfered edges, so they stay below the 0.05 m lidar band:

| Piece | Height | Place |
|---|---|---|
| Rumble strips | 0.020 m | Spine inside the gate |
| Road plates | 0.025 m | Spine, x 9..11 |
| Cable protector | 0.035 m | Tunnel entrance |
| Gravel patch | flush; friction 0.10 / 0.05 | Turnaround pocket |
| Mud patch | flush; friction 0.03 / 0.01 | Delivery yard |

A scenario sets `disturbances: true` to run with them; the same route without them is the
flat control row.

## 7. Work order

One commit per step or fix on `site-overhaul`; the user merges.

1. **Site plumbing on V1 only.** Resolver, `site` parameter and launch arguments, metadata
   `source_scene`, site-aware exporters, `site_open`, runner and demo changes. Exit: V1
   exports byte-identical, `scenario_spec` output for every V1 scenario unchanged apart from
   the new fields, one V1 smoke run.
2. **Pose heights.** FK script for the panel tops of `home`, `vertical_carry` and `carry` and
   H1 and H3 written to the kit spec.
3. **Kit.** Spec, Blender scripts, preview renders. **User checkpoint: review the previews.**
4. **SiteKit and V2 builder.** Spine, gate and building first. **User checkpoint: review
   Unity screenshots.** Then the remaining zones and the validator.
5. **V2 exports.** Map, boxes, metadata; map and box tests extended to V2.
6. **Tier 2.** Disturbance pieces and `site_disturbances`.
7. **Scenario set.** `scenario_spec` and plan-only checks.
8. **Smoke runs and real-time factor.** One run each with B1 and B5 on the tunnel, the
   1.05 m door, the chicane and the rough spine; the same B1 open-space drive on V1 and V2
   for the real-time factor. Long runs under `caffeinate`; Play stopped afterwards. These
   runs prove the site works; they are not baseline numbers.
9. **Documentation** (Section 9).

## 8. Testing

- Unity EditMode: spec to proxy placement; mesh-bounds check; validator cases (floating
  member, intersecting proxies, undersized door, short approach); V1 export byte-identity.
- ROS: resolver gtests (default site, duplicate names, site mismatch); `scenario_spec`
  regression over all V1 scenarios; `test_unity_nav2_map.py` and `test_planning_boxes.py`
  extended to V2.
- Runner: scene switch and disturbance toggle against a mocked Unity CLI
  (`tools/test_run_nav_scenario.py`).
- Blender: `build_kit.py` fails when an exported mesh's bounds differ from the spec by more
  than 0.02 m.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Proxy count grows from about 40 boxes to several hundred (scaffold tubes, pipes) | The MPC's broad phase only activates boxes within 0.8 m; MoveIt scene loading and MPC timing are measured on the tunnel smoke run. A problem goes into the comparability log and back to the user; the 0.02 m proxy rule is not relaxed silently. |
| Real-time factor below 1.00 | Baked lighting, then less dressing |
| Tier 2 pieces trip the lidar band when the base pitches | Heights at most 0.035 m with chamfers; smoke run `v2_spine_rough_nav` checks the costmap for phantom marks |
| H1 constraints conflict with the pose heights | Plan stops at step 2 and the user decides |
| Blender pieces late | Primitive placeholders from the spec keep Unity work going |

## 11. Open items after this design

- Overhead member H2 once a pose lower than carry is qualified.
- Switchable cross-fall (1-2 degrees) on one lane section.
- Slopes and ramps (Tier 3); they break the planar-base assumption and need their own phase.
- Visual worker figures on the mover boxes.
- One final baseline run on the final site before the thesis tables.

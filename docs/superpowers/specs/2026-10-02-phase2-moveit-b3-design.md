# Phase 2 design: Nav2 base navigation + MoveIt panel reconfiguration (baseline B3)

**Date:** 2026-10-02
**Branch:** `moveit-arm` (from `nav2-setup` at `804571b`)
**Roadmap:** Phase 2, baseline B3 (docs/roadmap.md Sections 2 and 8)

## 1. Purpose and scope

B3 is the decoupled mobile-manipulation baseline: Nav2 owns base navigation and
`/cmd_vel`, and MoveIt plans collision-free arm motion for the carried panel. Phase 2
exposes the gap between MoveIt's 3D knowledge and Nav2's fixed 2D footprint, which
Phase 3 (dynamic convex-hull footprint, B4) then addresses.

### Decisions taken in the design discussion

| Topic | Decision |
|---|---|
| Arm behaviour | The base stops, MoveIt plans and executes a collision-free reconfiguration, then the base drives again ("refined A"). |
| Arm motion while driving | Dropped from Phase 2 entirely; Phases 4-5 address it with whole-body MPC. |
| Goal form | Computed panel-pose goals with tolerances; named SRDF states are also accepted for plain restores. |
| Trigger | Scripted steps in the scenario definition. No route analysis (Phase 5 territory) and no failure-triggered retries. |
| Nav2 footprint | Fixed while driving; switched between named profiles only at standstill, after verifying that the reached arm/panel projection fits the new profile. |
| MoveIt collision world | Known geometry first (exported static boxes, scenario obstacles, padded floor); a lidar Octomap is added later in this phase. |
| Structure | A C++ `ReconfigurePanel` action server; the scenario runner sequences `NavigateToPose` and `ReconfigurePanel`. |
| Controllers | RPP, DWB, and stock MPPI, 3 runs each, matching Phase 1. |

### Out of scope

- Grasping, releasing, or re-attaching the panel; it stays rigidly attached as in Unity.
- MoveIt planning for the base, MoveIt Servo, Hybrid Planning, and MoveIt Task Constructor.
- Rerunning the Phase 1 scenarios without reconfiguration (open space, detour, worker
  crossing, blockage) under B3; B3 behaves as B1/B2 there.
- The pending Phase 1 rerun with the persistent global layer; it is done later, separately.

### Deferred options to keep visible

- **CHOMP post-processing** after OMPL, to add obstacle clearance and smoothness. Not in
  the initial pipeline; recorded as an open decision in the roadmap so it can be added
  as a B3 variant.

## 2. Unchanged contracts

- Nav2 Controller Server, through the collision monitor, is the only `/cmd_vel` publisher
  (ADR 0006). Nothing in Phase 2 publishes base commands or sends Nav2 goals except the
  scenario runner.
- The arm executes through `/arm_controller/follow_joint_trajectory` (JTC, 50 Hz) with
  the existing joint order and the arm recovery supervisor (ADR 0004, ADR 0005). Unity
  is not changed for arm control.
- Arm acceptance limits from `mobile_manipulator_control/config/qualified_payload.json`:
  path error 0.15 rad, hold error 0.06 rad, panel ground clearance 0.15 m, base tilt 3
  deg, no panel penetration.
- Footprint profiles stay in `mobile_manipulator_navigation/config/footprint_profiles.yaml`
  and keep their existing generation test.
- Simulation time, Cyclone DDS, and frames (`map -> odom -> base_footprint`) as in
  Phase 1.

## 3. MoveIt configuration

New package **`mobile_manipulator_moveit_config`**, generated once with the MoveIt Setup
Assistant and then maintained by hand. The URDF from `mobile_manipulator_description`
remains the only geometry source.

- **Planning group `arm`:** the six joints, chain `arm_mount_link` to `tool0`.
- **Named states:** `home`, `vertical_carry`, `level_extension`, equal to
  `qualified_payload.json` `poses_rad` (enforced by a test).
- **Self-collision matrix:** generated by the Setup Assistant and reviewed by hand.
- **Virtual joint:** `planar`, `map` to `base_footprint`, not part of any planning group.
  The base pose comes from TF so map-frame objects stay correctly placed; MoveIt never
  plans base motion.
- **Attached panel:** a 1.20 x 1.20 x 0.04 m box attached to `tool0`, using the same
  payload centre and size as the lidar self-filter's payload model. Allowed contacts:
  `tool0` and the last wrist link only. The object carries a **`panel` subframe** at
  its centre so goals refer to the panel rather than to `tool0`.
- **Kinematics:** KDL. pick_ik is the fallback if tolerance-based goal sampling proves
  unreliable.
- **Planning pipeline:** OMPL `RRTConnect` as the default planner; Ruckig time
  parameterization.
- **Limits:** `joint_limits.yaml` carries the design-ledger acceleration and jerk limits
  (enforced by a test); velocity and acceleration scaling 0.5 with the panel attached.
- **Execution:** MoveIt controller manager pointing at
  `/arm_controller/follow_joint_trajectory`.

### Known collision world

- **Static geometry:** a new Unity Pipeline command exports the axis-aligned box
  colliders under `Environment/NavigationObstacles` as a YAML list of boxes (ROS `map`
  frame, using the existing map-export coordinate conversion) into
  `mobile_manipulator_navigation/maps/`, alongside the 2D map, with a matching
  `validate` command, as for the 2D export.
- **Scenario obstacles:** the boxes from the active scenario in `scenarios.yaml`.
- **Floor:** a box whose top is at z = 0.15 m, so planning enforces the panel
  ground-clearance limit. Base links (chassis, wheels) and the arm mount, which
  legitimately sit below 0.15 m, may touch the floor object in the ACM; the arm links
  above the shoulder and the panel may not.
- **Loader node** (`planning_scene_loader`, C++) publishes these as collision objects
  and attaches the panel at startup.

## 4. `ReconfigurePanel` action

### Packages

- **`mobile_manipulator_interfaces`:** the `ReconfigurePanel` action definition.
- **`mobile_manipulator_manipulation`** (C++): the action server node and the planning
  scene loader.

### Interface

Goal:
- `target_type`: `PANEL_POSE` or `NAMED_STATE`.
- `panel_pose` (`geometry_msgs/PoseStamped`, frame `base_footprint`): target pose of the
  `panel` subframe.
- `position_tolerance` (`geometry_msgs/Vector3`, m): half extents of a box around the
  target position.
- `orientation_tolerance` (`geometry_msgs/Vector3`, rad): per-axis tolerance.
- `named_state` (string): SRDF state for `NAMED_STATE`.
- `footprint_profile` (string): profile from `footprint_profiles.yaml` to apply after
  success.
- `planning_time_s`, `planning_attempts`.

Result:
- `error_code`: `SUCCESS`, `BASE_NOT_STOPPED`, `ARM_NOT_ACTIVE`, `UNKNOWN_PROFILE`,
  `NO_IK`, `PLANNING_FAILED`, `PROFILE_TOO_SMALL`, `EXECUTION_FAILED`, `ARM_FAULT`,
  `PROFILE_VIOLATED_AFTER_EXECUTION`, `CANCELED`.
- Reached joint positions and reached `panel` pose.
- Applied footprint profile name and `profile_violated` (the measured state left the
  active profile after a failed or canceled execution).
- Containment margins (planned and measured state), in metres.
- Planning time, execution time, footprint-switch time.

Feedback: current phase (`CHECKING`, `PLANNING`, `VERIFYING_PLAN`, `EXECUTING`,
`VERIFYING_STATE`, `SWITCHING_FOOTPRINT`).

### Flow

1. **Preconditions:** the base is stopped (`/odom` linear speed below 0.01 m/s and yaw
   rate below 0.02 rad/s for 0.5 s), the arm hardware is active, and the profile exists.
2. **Plan** with MoveGroup: panel-pose goals become position and orientation goal
   constraints on the `panel` subframe; named states become joint goals.
3. **Verify the plan:** project the planned final state (URDF collision primitives plus
   panel) onto the ground plane; require it to lie inside the requested profile polygon.
   If not, return `PROFILE_TOO_SMALL` without moving.
4. **Execute** the trajectory through the JTC.
5. **Verify the reached state:** repeat the containment check on the measured
   `/joint_states` (the loaded arm droops).
6. **Switch the footprint:** publish the profile polygon on `/global_costmap/footprint`
   and `/local_costmap/footprint`. The collision monitor already follows
   `/local_costmap/published_footprint`.

### Footprint projection library

A small C++ library projects the URDF collision primitives plus the payload for a given
joint state onto the ground plane and tests containment in a polygon. It reuses the URDF
primitive and payload model that `lidar_robot_filter` already loads (moved into a shared
location if needed), and reproduces the bounds that `test_footprint_profiles.py`
computes for both profiles.

### Error handling

- Failure before execution: the arm has not moved; the footprint is unchanged.
- Execution failure, arm fault, or cancel (the trajectory is stopped first): the server
  reports `EXECUTION_FAILED`, `ARM_FAULT`, or `CANCELED`. It keeps the previous profile
  only if the measured state still fits it; otherwise the result also carries
  `profile_violated = true`. The runner aborts the mission without driving after any
  non-success result.
- The server never publishes `/cmd_vel` and never sends Nav2 goals; the "base stopped"
  check is a safety guard, not base authority.

## 5. Scenarios and runner

### Mission task

`scenarios.yaml` gains `task: mission` with a `steps` list:

```yaml
steps:
  - navigate: [x, y, yaw]
  - reconfigure:
      panel_pose: {xyz: [x, y, z], rpy: [r, p, y]}   # base_footprint
      position_tolerance: [dx, dy, dz]
      orientation_tolerance: [rx, ry, rz]
      footprint_profile: vertical_carry
  - reconfigure:
      named_state: home
      footprint_profile: home
```

A new C++ task `mission_scenario_task` runs the steps in order. It reuses the
`navigate_scenario_task` preflight checks and per-drive metrics and calls
`ReconfigurePanel` between drives. `tools/run_nav_scenario.py` still places the robot,
launches the stack, and collects output.

Runner validation before a run: every `navigate` pose and every pose at which a
`reconfigure` happens is free in the static map for both the profile active before and
the profile active after that step.

### B3 scenarios

| Scenario | Steps | Shows |
|---|---|---|
| 1.05 m gate with reconfiguration (roadmap 5) | start in `home`; drive to staging pose; reconfigure to a vertical panel pose with `vertical_carry`; drive through; restore `home`; drive to goal | Decoupled solution to the gate; compared against the Phase 1 `home` detour (`narrow_gate_home_nav`) on mission time |
| 1.30 m gate with reconfiguration | same | Reliable variant (the 1.05 m throat was marginal in Phase 1, 5/9) |
| Constrained reconfiguration | staging pose next to a wall or overhead box placed so that the qualified straight transition through `home` collides | MoveIt obstacle avoidance; an offline MoveIt validity check shows the naive transition is in collision (never executed in Unity) |

Each scenario runs with RPP, DWB, and MPPI, 3 runs each.

### Metrics

Per reconfiguration: planning success, attempts, IK failures, planning time; trajectory
duration and joint-space path length; minimum planned arm/panel distance to the
environment; JTC maximum path error and hold error; base tilt and panel ground clearance
(Unity ground truth); containment margin of planned and measured state; `move_group` CPU
and memory.

Per mission: success, total time, time stopped for reconfiguration, plus all Phase 1
navigation metrics per drive.

## 6. Octomap step (later in Phase 2)

- MoveIt `PointCloudOctomapUpdater` on `/livox/points_filtered`, 0.05 m resolution,
  5.0 m maximum range, MoveIt self-filtering enabled as a second layer.
- Each `reconfigure` step clears the Octomap, waits about 1 s of scans at standstill,
  then plans, so stale voxels from directionless misses cannot block planning.
- Launch argument `scene_source:=known|octomap`. In `octomap` mode the static boxes and
  floor stay known objects, but scenario obstacles are not published to MoveIt; they
  must be perceived, as Nav2 perceives them.
- Two extra scenarios: an unmapped box beside the staging pose that MoveIt must avoid,
  and a low box inside the documented near-field lidar blind zone, to measure and
  document that limitation.

## 7. Testing

- **Unit (gtest):** projection and containment against the Python profile bounds for
  `home` and `vertical_carry`; panel-pose goal to constraint conversion; mission step
  parsing and validation.
- **Configuration tests:** SRDF named states equal `qualified_payload.json`;
  `joint_limits.yaml` equals the design-ledger table; joint order equals
  `controllers.yaml`; the panel's allowed contacts are only `tool0` and the last wrist
  link.
- **Container integration without Unity:** MoveIt and the action server against
  ros2_control mock hardware (`use_mock_hardware:=true`), covering success, each
  precondition failure, `PROFILE_TOO_SMALL`, and cancel.
- **Unity runtime:** first re-qualify MoveIt-planned transitions against the acceptance
  limits in Section 2 (at 0.5 scaling they differ from the qualified 8 s cubic
  transitions through `home`; reduce scaling if they fail), then run the B3 missions.
